   Size: small


2. **B-33 · GoTrain · An export made after midnight is named for the day before**
   Why: `exportFilename` (~3195) takes the date from `toISOString()`, which is UTC. In Germany that is every export between 00:00 and 01:00 (winter) or 02:00 (summer): reproduced with `TZ=Europe/Berlin` at 00:30 CEST on 16 Oct → `gotrain-2026-10-15.json`. The file then looks like yesterday's backup next to the real one. The history entry's own `date` is already local (`saveHistory` ~3460); only the filename disagrees. Build the date from `getFullYear/getMonth/getDate`.
   Verify: browser test with Chromium started under `TZ=Europe/Berlin` (or with `Date` stubbed to 2026-10-16T00:30+02:00): the name is `gotrain-2026-10-16.json`; a midday export is unchanged.
   Size: small


3. **B-43 · omarchy-gotrain · Show how long each workout took, now that the phone records it**
   Why: since GoTrain v42 (PR #17) every finished workout carries `startTs`, when its first set was ticked, beside `ts` (Finish), and the app's History shows the span. The archive already keeps it, since `ingest` stores each workout's full JSON in `workouts.json`, but nothing reads it: `list`, `show`, the panel's recent list and `export --csv` show no duration. Read it at query time from `json`, so there is no schema migration: minutes from `startTs` to `ts`, only when both parse and the span is positive and under 24 hours, the same rule as the app's `entryMinutes`. Older workouts have no `startTs` and show nothing, not 0.
   Verify: new test: a workout with `startTs` 50 minutes before `ts` shows "50 min" in `list` and `show`, the panel JSON carries a duration of 50 for it, and the CSV has a new last column with 50 (existing columns keep their order, so a sheet built on the old CSV still lines up). One without `startTs`, or with a span over a day, shows no duration and an empty CSV cell.
   Size: small


4. **B-40 · omarchy-gotrain · `list -n 0` says "no workouts yet" and `list -n -1` lists everything**
   Why: `cmd_list` (~1486) and `cmd_panel` (~1434) pass `-n` straight into SQLite's `LIMIT ?`, where 0 means no rows and a negative number means no limit. Reproduced again tonight (1.4.4, the `tests/fixtures/baseline.json` archive of 3 workouts): `list -n 0` prints "no workouts yet" and exits 0, which reads as an empty archive; `list -n -1` prints all 3; `panel -n -1` returns everything as `recent`. "No workouts yet" over a full archive is exactly the false alarm about the user's only copy that the archive rules care about, and on a 3000-workout archive `-n -1` dumps everything into the panel's JSON. Reject `-n` below 1 at argument parsing (an argparse `type` that requires a positive int, shared by `list` and `panel`) so the error names the option and exits 2, the way argparse already does for `-n abc`.
   Verify: new test: `list -n 0` and `list -n -1` exit non-zero with a message naming `-n` and print no workout lines; `panel -n 0` likewise; `list -n 1` prints one line and the default still prints up to 15; an empty archive still says "no workouts yet".
   Size: small


5. **B-34 · omarchy-gotrain · `stats` prints its first/last dates in UTC, so it disagrees with `list`**
   Why: `cmd_stats` (~1607) prints `span['a'][:10]`, the first ten characters of the stored text, which for app workouts is the UTC date. B-6 moved every other day to local time, so the commands now contradict each other. Reproduced with `TZ=Europe/Berlin` and two workouts at 00:30 and 00:40 local (`ts` 22:30Z/22:40Z the day before): `list` shows 2026-10-02 and 2026-10-16, `stats` says "first / last : 2026-10-01 .. 2026-10-15". Every late-evening-into-midnight session is off by one. The code is unchanged in 1.4.4 (B-24 made `stats` *pick* the first and last entries by instant, but it still prints the raw text). Use `local_date()` as `today` and `list` already do; a row whose `ts` cannot be parsed keeps today's fallback.
   Verify: new test with that fixture under `TZ=Europe/Berlin`: `stats` prints `2026-10-02 .. 2026-10-16`, matching `list`; a midday workout's date is unchanged; a legacy `+02:00` timestamp gives its own local date.
   Size: small


6. **B-45 · omarchy-gotrain · `export -o` into a folder, or a folder that does not exist, ends in a traceback**
   Why: `cmd_export` (~1686) hands `-o` straight to `Path.write_text`, for both the JSON and `--csv`. Reproduced tonight (1.4.4, `tests/fixtures/baseline.json` archive): `export -o ~/Downloads` — the natural thing to type when the file is meant for the phone — prints an `IsADirectoryError` traceback and exits 1; `-o missing/dir/out.json` prints `FileNotFoundError`. A traceback from the command that makes the user's backup reads like archive damage. The same write also truncates an existing file before writing it, so a write that fails part-way (disk full) destroys the previous backup at that path. Refuse a directory and a missing parent with a one-line `die()` that names the path, and write to a temporary file beside the target, then `os.replace` it, so the old file survives any failure. Do not invent a file name inside the folder: a `gotrain-*.json` written into the watch folder would itself be picked up by `sync`.
   Verify: new test: `export -o <dir>` and `export --csv -o <dir>` exit non-zero with the path in the message and no `Traceback`; a missing parent likewise; `-o file.json` still writes the same JSON as before and prints its count; with an existing file at the target and the write made to fail (a monkeypatched `json.dumps` or a read-only directory), the old file's contents are unchanged and no temporary file is left behind.
   Size: small

9. **B-48 · omarchy-gotrain · README lists `origin` as a config key, but a set `origin` is silently ignored**
   Why: README.md ~240 ends its section with "Config keys: `watchDirs`, `watchGlobs`, `port`, `maxUrlPayload`, `pairTimeout`, `staleDays`, `origin`, `appUrl`." But `load_config` (~244) always overwrites `cfg["origin"]` with `origin_of(appUrl)`, on purpose (its comment: two values could disagree and the receiver would allow the wrong site), and the README's own pairing section (~156) already says the origin follows the address. Reproduced tonight (1.4.4, throwaway `XDG_CONFIG_HOME`): `config set origin https://example.org` → "unknown setting 'origin'. Editable: appUrl, pairTimeout, port, staleDays, watchDir"; `config get origin` likewise; an `origin` written into config.json by hand is accepted without a word and has no effect. The people who read that line are the ones self-hosting, and they would set `origin` and then wonder why pairing is refused. The same line also names `watchDirs`, while `config set` takes `watchDir`. Rewrite the line to list the keys `gotrain config set` accepts, say that `origin` is derived from `appUrl` and cannot be set, and keep the hand-edit-only keys (`watchGlobs`, `maxUrlPayload`, the list form `watchDirs`) as a separate, labelled sentence. Optionally, `load_config` prints one stderr line when config.json holds an `origin` that differs from the derived one, the way it already reports a rejected value.
   Verify: the README's key list matches `EDITABLE` plus the documented hand-edit keys, and no longer offers `origin` as a setting; if the warning is added, a new test writes `{"origin":"https://example.org"}` to config.json and checks that `status --json` still exits 0 with its usual JSON on stdout and the warning on stderr, and that a config without `origin`, or with the derived one, prints nothing.
   Size: small

10. **B-49 · GoTrain · The 20-set cap is written out in seven places**
   Why: follow-up from PR #20 (B-42, v43), added at the owner's request. Since v43 every place that takes a set count stops at 20, but each spells the 20 itself: `parseSetCount` (~2949, `Math.min(20,…)`), `normaliseSetCounts` (~1300-1301, `n<=20` and `Math.min(20,n)`), `saveAdjust` (~1991, `Math.min(20,n)`), the adjust field in `ADJUST_FIELDS` (~1943, `max:20`), the library exercise editor's `#gex-sets` (~668, `max="20"` in static HTML) and the plan exercise editor's `#mce-sets` (~3029, `max="20"` in its template). Changing the cap means finding all seven, and missing one brings back exactly the disagreement B-36, B-41 and B-42 fixed. Add one `const MAX_SETS=20` beside `parseSetCount` and use it in all of them: the template and `ADJUST_FIELDS` can interpolate it; the static `#gex-sets` either gets its `max` set from `MAX_SETS` when the editor opens, or the comment beside it names the constant. Behaviour stays the same; this is a cleanup only. `saveAdjust`'s rule for below 1 ("no change for today") stays different from the editors' on purpose.
   Verify: `tests/run` passes unchanged (the B-36/B-41/B-42 tests already cover each path's behaviour at 20); a new static check in `tests/run` finds no `Math.min(20` or `<=20` left in `index.html`; a browser test reads `max` on `#gex-sets`, `#mce-sets` and `#adj-sets` and gets `String(MAX_SETS)` for each.
   Size: small
